# Setting up Claude Code for research projects

A guide for going from "one folder per project" to something Claude can actually work in.
It describes a shape, not a prescription: the parts marked *essential* are worth copying,
the rest is taste and you should pick your own names.

## What is actually wrong with one folder per project

Nothing, structurally. The problem is that none of those folders tell Claude anything, so
every session starts from zero. You re-explain where the data lives, which R version, what
the project is about, which script is the entry point, and what it must never overwrite.
That re-explaining is the whole cost, and it is fixed by writing the explanation down once
per project in a place Claude reads automatically.

Three layers do that. A fourth is optional.

## Layer 1: the global layer (`~/.claude/`)

Applies to every project on the machine. Two files.

`~/.claude/CLAUDE.md` is your standing context: who you are, what you work on, and how you
want to be answered. Keep it to 20 or 40 lines. It is loaded into every single session, so
length here is a tax you pay constantly.

What belongs in it:

- field, institution, what you actually do
- tool defaults (R or Python, tidyverse or base, `targets` or plain scripts, Quarto or Rmd)
- writing register for scientific text, citation style, units
- how you want disagreement handled (most useful single line: ask it to flag unsupported
  claims and push back on vague phrasing instead of agreeing)
- output style: concise, prose over bullet lists, no motivational filler

What does not belong in it: project specifics, file paths, credentials, or a long style
guide. Project specifics go in layer 2. Credentials go nowhere.

`~/.claude/settings.json` holds machine-wide permissions and defaults. Start it empty and
add to it only when something annoys you twice.

Both files are editable with `/memory` from inside a session, and a line typed with a
leading `#` gets appended to one of them, which is the low-friction way to build the file
up over a few weeks instead of writing it in one sitting.

## Layer 2: the project layer (*essential*)

Two files in every project root.

### `CLAUDE.md`

Committed to git, read automatically whenever a session starts in that folder. Aim for
about 30 lines. A usable skeleton:

```markdown
# Project: <one line, what question this answers>

## Data
- Raw data: data/raw/ (read-only, never modify or regenerate)
- Provenance: <instrument / collaborator / database, and when it arrived>
- Processed data in data/processed/ is generated by R/01_clean.R and is disposable

## Running it
- renv project, R 4.4. `renv::restore()` first.
- Entry point: analysis/run_all.R

## Conventions
- Figures to output/figures/ as PDF, 180 mm wide, via ggsave()
- Species names follow <reference list>
- Site codes are <scheme>

## Hard rules
- Never write into data/raw/
- Never commit anything over 20 MB
- Do not change the pre-registered model structure in R/04_models.R without asking
```

Two tips that save time. First, `/init` in an existing project generates a draft CLAUDE.md
by reading the code; it is the fastest start, but generated files are consistently too long
and too descriptive, so cut it by half and replace the description with rules. Second, when
Claude does something you did not want, the fix is usually one new line in CLAUDE.md rather
than a longer prompt next time.

### `.claude/settings.json`

Permissions for this project. Deny rules are the important half, because they are what lets
you work quickly without worrying. The pattern:

```json
{
  "permissions": {
    "deny": [
      "Read(./.env)",
      "Read(./.env.*)",
      "Read(./**/secrets/**)",
      "Read(./**/*.pem)",
      "Read(./**/*.key)",
      "Edit(./data/raw/**)",
      "Write(./data/raw/**)"
    ],
    "allow": [
      "Bash(git status)",
      "Bash(git diff:*)",
      "Bash(Rscript:*)"
    ]
  }
}
```

The deny entries on `data/raw/` are the ones worth copying even if you skip everything else
in this guide. Field data that exists in one copy should be structurally unwritable, not
protected by you remembering to say so.

The `allow` list only suppresses permission prompts for things you would always approve
anyway. Build it up from whatever you find yourself clicking through.

If a path is specific to your laptop and should not be committed, put it in
`.claude/settings.local.json` instead and gitignore that file.

Also add to `.gitignore`:

```
.claude/logs/
data/processed/
output/
```

## Layer 3: one skeleton, reused (*essential in spirit, not in naming*)

The point of a fixed folder layout is not tidiness. It is that instructions become
transferable: once "raw is immutable, output is disposable" is true in all your projects,
you stop having to say it.

```
project-name/
  README.md               human-facing: what, who, status
  CLAUDE.md               machine-facing: rules, paths, conventions
  .claude/settings.json
  data/
    raw/                  as it came off the instrument or from a collaborator. immutable.
    processed/            generated, reproducible, gitignored
  R/                      functions and numbered pipeline steps
  analysis/               the scripts or notebooks you actually run
  output/
    figures/
    tables/
  docs/                   protocols, notes, manuscript drafts
  renv.lock               or environment.yml / requirements.txt
```

Pick your own names freely. `src/` or `scripts/` instead of `R/`, `results/` instead of
`output/`, `manuscript/` split out of `docs/`. What matters is that you choose once and then
do not vary it between projects, because the consistency is the thing Claude exploits, not
the vocabulary.

The only two invariants worth defending: nothing is ever written into `data/raw/`, and
everything in `output/` can be deleted and regenerated from code. If both hold, you can let
Claude work much more freely, because the worst case is a rerun.

### Where the folders live

One flat parent directory, one git repo per project:

```
~/research/
  lake-macrophytes-2025/
  edna-validation/
  dom-fluorescence/
```

Flat, not nested by year or collaborator. You open Claude Code in a project root so that it
sees exactly one project, and nesting just makes that harder. Keep teaching, admin and
personal notes outside this tree.

## Making it repeatable

Once the skeleton has stopped changing, stop creating it by hand.

A template folder plus a shell function is enough:

```bash
mkdir -p ~/templates/research-project/{data/raw,data/processed,R,analysis,output/figures,output/tables,docs,.claude}
# put your CLAUDE.md, .claude/settings.json, .gitignore and README.md stubs in there

# in ~/.zshrc or ~/.bashrc
newproj() {
  cp -r ~/templates/research-project ~/research/"$1"
  cd ~/research/"$1" || return
  git init -q && git add -A && git commit -qm "chore: scaffold project"
  echo "ready: $PWD  (now edit CLAUDE.md)"
}
```

If you work on two machines, a GitHub template repository is the better version of the same
idea: click "Use this template" and clone.

## Optional layer 4: skills

When you notice yourself giving the same multi-step instruction for the third time ("make
this figure in the group's style", "check this paragraph against the journal's author
guidelines", "run the standard QC on a new plankton count"), that repetition is a skill:
a folder in `~/.claude/skills/<name>/` containing a `SKILL.md` with a description and the
steps. Claude loads it when the task matches.

Deliberately last. Skills written before the repetition is real tend to be wrong about what
the repetition actually was.

## Migration, in this order

The single most common failure is spending a weekend reorganising twelve folders and then
not using the result.

1. Pick the one project you are actively working in this week. Leave the others alone.
2. Add `CLAUDE.md` and `.claude/settings.json` to it. Run `/init` if you want a draft, then
   cut it down.
3. Work normally for a week. Every time Claude gets something wrong about the project, add
   one line instead of correcting it in chat.
4. When that CLAUDE.md has gone a few days without changing, copy it into the template and
   generalise the project-specific bits.
5. Retrofit old projects lazily, at the moment you next open one, never in a batch.

## Worth getting right early

Git in every project from day one, even solo, even with no remote. It is what makes
reviewing Claude's work cheap (you read a diff) and mistakes free (you revert). This is a
bigger quality-of-life difference than anything else in this guide.

Large and sensitive data out of git. Leave raw data where it belongs (institutional storage,
NAS, external drive), gitignore it, and put the path in CLAUDE.md instead of the data. If a
dataset is unpublished, permit-restricted or personal-data-adjacent, decide consciously
which folders Claude may read and write the deny rules accordingly rather than assuming.

Nothing secret in CLAUDE.md. It is committed and it is the first file anyone reads.
API keys, tokens and passwords belong in `.env` (gitignored, and denied above).

One session per project. Launching Claude Code in `~/research/` so it can see everything at
once sounds convenient and reliably produces worse results than opening it in one project.

## The one-paragraph version

Use the same folder skeleton in every project. Put a short `CLAUDE.md` in each one saying
what the project is, where the data came from, how to run it, and what must not be touched.
Keep a short global `~/.claude/CLAUDE.md` for how you want to be written to. Add deny rules
so raw data cannot be overwritten. Use git everywhere. Everything past that is optimisation,
and you will know which parts you need after two weeks of actually using it.
